# API Endpoint Caching Plan

## Goal

Cache API endpoints whose data changes infrequently (lookup tables, reference data, rarely-mutated configuration) to reduce database load, improve response latency, and decrease Redis pressure from hot paths. Redis is already deployed and configured (used for rate limiting per `main.py:82-153` and `config.py:81`), so it will serve as the cache backend.

---

## Cacheable Endpoints Identified

Analysis of all endpoints (`/api/v1/__init__.py:16-25`) cross-referenced with frontend call patterns (`frontend/lib/api.ts`, `frontend/app/admin/page.tsx`, `frontend/components/CreateBatchModal.tsx`, `frontend/components/BatchDetailDrawer.tsx`):

### Tier 1 — Static Lookup Tables (long TTL, invalidate on mutation)

| # | Endpoint | Controller | Service Method | Data Size | Mutation Endpoints | Current Call Frequency |
|---|----------|------------|----------------|-----------|--------------------|--------------------|
| 1 | `GET /batch-options/{type}` | `batch_options/controller.py:57` | `BatchService.list_options` → `BatchRepository.list_active_options` | ~3-10 rows each | `POST`/`PATCH`/`DELETE /batch-options/{type}` (admin only) | Called 6+ times per page load in CreateBatchModal, BatchDetailDrawer, Admin page (8 option types) |

**Analysis:** These four endpoint families return reference/enum-like data that is only ever modified through dedicated Admin-only mutation endpoints. ## Cache Design

### Technology Stack

- **Backend:** `redis==5.0.1` already in `requirements.txt:22`; used by `RedisRateLimitMiddleware` in `main.py:82-153`.
- **Connection:** Reuse the existing Redis client pattern from `main.py:90-108` (`redis.Redis(host=settings.REDIS_HOST, port=settings.REDIS_PORT, password=settings.REDIS_PASSWORD)`).
- **Serialization:** `json` for simple payloads; `msgspec` or `orjson` not currently in deps — use stdlib `json` with Pydantic `.model_dump_json()` / `TypeModel.model_validate_json()`.

### Cache Service

**New file:** `backend/app/core/cache.py`

```python
class RedisCacheService:
    def __init__(self, redis_url: Optional[str] = None):
        # Lazily connect, with the same config as RedisRateLimitMiddleware
        self._redis = redis.Redis(
            host=settings.REDIS_HOST,
            port=settings.REDIS_PORT,
            password=settings.REDIS_PASSWORD,
            db=settings.REDIS_DB,
            decode_responses=True,
            socket_connect_timeout=2,
            socket_timeout=2,
        )
        self._prefix = "ops_cache"

    def _key(self, namespace: str, identifier: str) -> str:
        return f"{self._prefix}:{namespace}:{identifier}"

    async def aget(self, namespace: str, identifier: str) -> Optional[str]:
        try:
            return await self._redis.get(self._key(namespace, identifier))
        except redis.ConnectionError:
            return None  # fail-open: skip cache, hit DB

    async def aset(self, namespace: str, identifier: str, value: str, ttl: int) -> None:
        try:
            await self._redis.setex(self._key(namespace, identifier), ttl, value)
        except redis.ConnectionError:
            pass  # fail-open

    async def adelete(self, namespace: str, identifier: str) -> None:
        try:
            await self._redis.delete(self._key(namespace, identifier))
        except redis.ConnectionError:
            pass

    # Sync variants for sync service methods
    def get(self, namespace, identifier) -> Optional[str]
    def set(self, namespace, identifier, value, ttl) -> None
    def delete(self, namespace, identifier) -> None
```

**Note on sync vs async:** The services currently use sync SQLAlchemy (`Session`), so the service layer is synchronous. A synchronous Redis client (`redis.Redis`) is appropriate here. If async is preferred, the service methods would need to become `async`, which is a larger refactor. Recommendation: sync client for Phase 1.

### TTL Policy

| Tier | Endpoints | TTL | Rationale |
|------|-----------|-----|-----------|
| Static lookups | batch-options, teams, roles, approval-config | 10 min | Only changes via Admin mutation; 10 min staleness acceptable for reference data |
| Semi-static | faculty list, assignable users | 5 min | Roster changes on hire/fire; Admin UI can tolerate minutes of staleness |
| Scoped user data | my-reports | 2 min | Report hierarchy may change more frequently |
| Real-time aggregations | manager-dashboard | 60s | Operational dashboard; users expect near-real-time but caching reduces query load |

### Cache Invalidation Strategy

**Write-through invalidation** — delete the cache key after successful mutation, not before:

```python
# In controller after successful mutate:
cache_service.delete("v1:options", option_type)  # invalidates the list

# In service after successful create:
self.cache.delete("v1:options", option_type)
```

**Invalidation map:**

| Mutation Endpoint | Cache Keys to Invalidate |
|-------------------|--------------------------|
| `POST /batch-options/{type}` | `v1:options:{type}` |
| `PATCH /batch-options/{type}/{id}` | `v1:options:{type}` |
| `DELETE /batch-options/{type}/{id}` | `v1:options:{type}` |
| `POST /teams` | `v1:teams:default` |
| `PATCH /teams/{id}` | `v1:teams:default` |
| `DELETE /teams/{id}` | `v1:teams:default` |
| `POST /roles` | `v1:roles:default` |
| `PATCH /roles/{id}` | `v1:roles:default` |
| `DELETE /roles/{id}` | `v1:roles:default` |
| `PUT /batches/approval-config` | `v1:approval-config:default` |
| `POST /auth/users` | `v1:users:assignable:{role}`, `v1:faculty:all` (if role=Faculty) |
| `PATCH /auth/users/{id}` | `v1:users:assignable:{old_role}`, `v1:users:assignable:{new_role}` |
| `DELETE /auth/users/{id}` | `v1:users:assignable:{role}`, `v1:faculty:all` |

## Implementation

### Phase 1 — Cache Service & Dependency Injection

1. **Create `backend/app/core/cache.py`** with `RedisCacheService` (sync client).
2. **Add `get_cache` dependency** in `backend/app/api/deps_services.py`:
   ```python
   def get_cache() -> RedisCacheService:
       return RedisCacheService()
   ```
3. **Inject `RedisCacheService`** into `BatchService`, `TeamService`, `RoleService`, `FacultyService`, `AuthService`, `AnalyticsService`.

**Acceptance:**
- `RedisCacheService` connects to Redis with the same config as `RedisRateLimitMiddleware`.
- Cache failures (Redis down) fail open — requests proceed to DB.
- No changes to API responses in this phase.

### Phase 2 — Cache Tier 1: Static Lookup Tables

Cache: `GET /batch-options/{type}`, `GET /teams`, `GET /roles`, `GET /batches/approval-config`.

**Approach:** Cache-Aside (Lazy Loading).

```python
# In BatchService.list_options:
def list_options(self, option_model):
    option_type = self._option_type_name(option_model)
    cache_key = f"options:{option_type}"
    cached = self.cache.get("v1", cache_key)
    if cached:
        return parse_obj_as(List[OptionResponse], json.loads(cached))
    
    result = self.batch_repo.list_active_options(option_model)
    self.cache.set("v1", cache_key, json.dumps([r.model_dump() for r in result]), ttl=600)
    return result
```

**Invalidation in mutation endpoints:**
- `batch_options/controller.py:66-73` (`create_option`): add `cache.delete("v1", f"options:{option_type}")`
- `batch_options/controller.py:76-84` (`update_option`): same
- `batch_options/controller.py:87-93` (`deactivate_option`): same
- `teams/controller.py:36-43` (`create_team`): add `cache.delete("v1", "teams:default")`
- `teams/controller.py:56-63` (`update_team`): same
- `teams/controller.py:67-72` (`delete_team`): same
- `roles/controller.py:35-42` (`create_role`): add `cache.delete("v1", "roles:default")`
- `roles/controller.py:55-63` (`update_role`): same
- `roles/controller.py:66-72` (`delete_role`): same
- `batches/controller.py:81-87` (`update_approval_config`): add `cache.delete("v1", "approval-config:default")`

**Acceptance:**
- Warm cache: second call to same endpoint returns from Redis without hitting DB.
- Cold cache: first call populates cache.
- Mutation: cache invalidated, next read repopulates from DB.

### Phase 3 — Cache Tier 2: Semi-static Rosters

Cache: `GET /faculty`, `GET /auth/users/assignable`, `GET /auth/my-reports`.

**Approach:** Cache-Aside with shorter TTL (5 min for faculty/assignable, 2 min for my-reports).

```python
# In FacultyService.list:
cached = self.cache.get("v1", "faculty:all")
if cached:
    return json.loads(cached)

result = [self._to_response(f) for f in self.faculty_repo.list_active_faculty()]
self.cache.set("v1", "faculty:all", json.dumps(result), ttl=300)
return result
```

**Invalidation:** On `POST /auth/users`, `PATCH /auth/users/{id}`, `DELETE /auth/users/{id}` — invalidate `v1:users:assignable:{role}` for affected role, plus `v1:faculty:all` if role is Faculty.

**Note:** The `/auth/users` list endpoint (`require_manager_or_admin`) is NOT cached here — it may be addressed in the security plan. Focus on `assignable` and `faculty`.

**Acceptance:**
- Faculty roster cached for 5 min.
- Cache invalidated when a Faculty user is created, updated, or deleted.

### Phase 4 — Cache Tier 3: Manager Dashboard

Cache: `GET /analytics/manager-dashboard`.

**Approach:** Cache-Aside with 60s TTL, user-scoped key.

```python
# In AnalyticsService.manager_dashboard:
cache_key = f"analytics:dashboard:{current_user.id}"
cached = self.cache.get("v1", cache_key)
if cached:
    return ManagerDashboardSummary.model_validate_json(cached)

result = self._compute_dashboard(...)
self.cache.set("v1", cache_key, result.model_dump_json(), ttl=60)
return result
```

**Invalidation:** Invalidate on session creation/update/cancel (sessions/controller.py mutation endpoints), batch status change (batches/controller.py lifecycle endpoints), and gate completion (sessions/controller.py `complete_session_gate1`). Add to each of these controller methods.

**Acceptance:**
- Dashboard cached per-user for 60s.
- Cache invalidated when any session or batch status changes for that user's scope.

### Phase 5 — Testable Cache Wrapper

**New file:** `backend/app/core/cache_decorator.py` — a decorator for cache-aside pattern to reduce boilerplate.

```python
def cached(namespace: str, ttl: int, key_fn: Callable):
    def decorator(func):
        @wraps(func)
        def wrapper(self, *args, **kwargs):
            cache_key = key_fn(*args, **kwargs)
            cached_val = self.cache.get(namespace, cache_key)
            if cached_val is not None:
                try:
                    return json.loads(cached_val)
                except (json.JSONDecodeError, TypeError):
                    pass  # fall through to recompute
            result = func(self, *args, **kwargs)
            try:
                serialized = result.model_dump_json() if hasattr(result, 'model_dump_json') else json.dumps(result)
                self.cache.set(namespace, cache_key, serialized, ttl)
            except (TypeError, ValueError):
                pass  # log at debug, don't cache if not serializable
            return result
        return wrapper
    return decorator
```

**Note:** Decorator approach is optional — direct `cache.get`/`cache.set` calls in service methods are simpler and more debuggable.

## Rollout / Migration Path

| Step | Change | Risk | Rollback |
|------|--------|------|----------|
| 1 | Add `RedisCacheService` + DI | Low | Remove DI injection |
| 2 | Cache Tier 1 (lookups) | Low — read-only path; cache miss = DB | Set TTL to 0 or remove cache calls |
| 3 | Cache Tier 2 (rosters) | Low | Same |
| 4 | Cache Tier 3 (dashboard) | Low | Same |
| 5 | Add invalidation to mutations | Medium — must not break write paths | Remove cache.delete calls |

**Deployment notes:**
- Redis is already required by `docker-compose.yml` (service `redis:`, port 6379). No new infra needed.
- Cache TTLs are conservative (2-10 min) to ensure data freshness during rollout.
- Cache is fail-open: Redis unavailable → all reads fall through to DB.

## Out of Scope

- **Frontend request deduplication** — the frontend's `ApiError` retry-on-401 already prevents duplicate requests via the refresh promise cache (`api.ts:558`); the new cache layer is server-side only.
- **Cross-endpoint cache invalidation** — e.g., creating a Batch does not invalidate the faculty cache. Only user/faculty mutation endpoints invalidate user/faculty caches.
- **ETag/Last-Modified conditional caching** — not implemented; Redis TTL is the sole invalidation signal.
- **Response caching at Nginx** — Nginx `proxy_cache` could also be used but the Redis approach allows fine-grained key-based invalidation which Nginx cannot do for authenticated endpoints.
